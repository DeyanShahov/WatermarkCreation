## 1. Общ преглед

### 1.1 Какво е проектът
**WatermarkCreation** е локално PWA уеб приложение (Vanilla JS + Vite + IndexedDB + Canvas) за водни знакове на снимки с GPS, метео данни, QR код, категории и стъпки. Работи офлайн, без сървър — всички данни остават в браузъра.

### 1.2 Какъв проблем решава новата функционалност
Техниците получават **десетки снимки от един обект** (авария, ремонт) и трябва ръчно да преглеждат всяка, да я разпознават и да я поставят на правилното място в категория/стъпки. Това отнема **часове**.

Новият **AI vision модул** автоматизира този процес:
1. **Извлича водния знак** от всяка снимка (дата, час, град, точен адрес — предимно на немски, но и други езици) → запаметява стойностите към снимката за по-нататъшна обработка.
2. **Анализира съдържанието** (скъсан кабел, наранена тръба, изкоп, свързани елементи…) и го сравнява с **очакваното съдържание, дефинирано от потребителя за всяка стъпка**.
3. **Разпределя автоматично** снимките в избраната категория/стъпки, с хронологична наредба, предупреждения и доклад.

### 1.3 За кого е
- **Основен потребител:** технически ръководител/инженер (RedFox), който документира аварии и ремонти на терен (Германия/България).
- **Работен контекст:** една задача наведнъж — изчистена галерия, снимки **само от един обект**, предварително създадена категория със стъпки.

### 1.4 Работен поток (фиксиран с потребителя)

```
┌─────────────────────────────────────────────────────────────────┐
│ 1. Потребителят изчиства галерията и зарежда снимки от ЕДИН обект │
│ 2. Предварително е създал Категория → Стъпки                     │
│    (всяка стъпка има „Описание" = какво се очаква на снимката)    │
│ 3. Избира път:                                                   │
│    ├─ (а) РЪЧЕН: преглед една по една → присвояване (както сега)  │
│    └─ (б) AI: бутон „🤖 AI сортиране" → модал:                    │
│         • избор на категория                                     │
│         • AI настройки (endpoint/key/model, праг, force)         │
│         • „Стартирай AI анализ"                                  │
│ 4. AI анализира ВСЯКА снимка (воден знак + съдържание, 1 заявка)  │
│ 5. Кръстосва AI резултата с EXIF + воден знак + адрес на категория│
│ 6. Автоматично нареждане в категорията/стъпките (хронологично)    │
│ 7. Доклад (по избор): коя снимка къде, съвпадение, увереност %,   │
│    извлечени метаданни, предупреждения                            │
│ 8. Галерията показва цялата извлечена мета информация + баджове   │
│ 9. Потребителят може да коригира ръчно (drag & drop, както сега)  │
└─────────────────────────────────────────────────────────────────┘
```

### 1.5 Пример (от потребителя)
Категория „Авария скъсан кабел":
- Стъпка 1 „Заварено положение" — описание: „дупка/изкоп и скъсан кабел", необходими 2 снимки
- Стъпка 2 „Ремонт" — описание: „свързани кабели, поправена тръба", необходими 3 снимки

5 снимки с воден знак (дата, час, град, адрес):
- 2 показват изкоп + скъсан кабел → **Стъпка 1**, наредени по час
- 3 показват свързани елементи → **Стъпка 2**, наредени по час
- Снимка с друг адрес → **неприсвоена**, бадж „възможен друг обект"
- Снимка без съвпадение → **неприсвоена**, бадж „нерелевантна" + причина

### 2.2 Нов / разширен
| Компонент | Решение |
|---|---|
| **Vision AI модел** | `qwen/qwen3.8-27b` (OpenAI-compatible chat completions с `image_url` съдържание). **Конфигурируем** — потребителят може да смени модела. ⚠️ Наличието на vision поддръжка за този модел в Groq трябва да се верифицира (Фаза 0). |
| **AI връзка (хибрид)** | **Локален ключ с приоритет** → директно браузър → Groq (снимките НЕ минават през Netlify). **При липса на ключ** → Netlify proxy `ai-process.js` (ключът остава сървърен; снимките преминават през Netlify само като транзит в паметта). |
| **Нови модули** | `src/core/ai-vision.js` (vision клиент + routing), `src/core/ai-sorter.js` (оркестрация: анализ → сравнение → разпределение → доклад) |
| **Разширен proxy** | `netlify/functions/ai-process.js` — добавяне на vision поддръжка (`image` base64 + `context`), запазвайки съществуващите текстови действия |
| **Съхранение на AI резултати** | Разширение на photo записа в съществуващия `photos` store (IndexedDB е schemaless — без миграция) |
| **UI** | Нов модал „AI сортиране", доклад модал, баджове в галерията, AI панел в preview модала |

### 2.3 Без нови тежки зависимости
Цялата имплементация остава **vanilla JS**. Единствената съществуваща dependency (`qrcode-generator`) не се засяга. Base64 енкодирането и downscale-ът използват вградени browser API-та (FileReader, Canvas).

### 3.2 Хибриден routing (фиксирано решение)

```
getEffectiveAISettings(categoryId)  →  { endpoint, apiKey, model, prompt }
        │
        ├─ apiKey Е НАЛИЦЕН (локален, от IndexedDB)
        │     └─▶ ДИРЕКТНО: fetch(endpoint, { Authorization: Bearer apiKey,
        │                      messages: [system, {role:user, content:[image_url, text]}] })
        │         • снимките отиват ПРАВО към Groq, НЕ минават през Netlify
        │         • ключът живее само в браузъра
        │
        └─ apiKey НЯМА
              └─▶ PROXY: POST /.netlify/functions/ai-process
                         { action:'analyze-image', image:base64, context:{steps, address}, model }
                  • Netlify прикача сървърния ключ (GROQ_API_KEY env)
                  • снимката преминава през Netlify САМО като транзит (в паметта,
                    не се записва/логва по подразбиране)
                  • изисква Netlify deployment
```

> **Принцип на поверителност:** При AI анализ снимката **винаги напуска устройството** — тя трябва да стигне до AI доставчика (Groq), за да бъде анализирана. Това е неизбежно и важи за двата пътя. Разликата е дали минава и през Netlify като междинна спирка. Локалният ключ (директният път) е с приоритет именно за да се избегне този транзит, когато потребителят има свой ключ.

### 3.3 Поток на данни за една снимка

```
photo.file (Blob)
   │
   ├─▶ exif.readExifData(file) ──────────────▶ { dateTime, gps, make, model }
   │
   ├─▶ downscale(file, maxEdge=1600, q=0.8) ─▶ base64 JPEG (анализно копие;
   │                                            оригиналът НЕ се пипа)
   │
   └─▶ ai-vision.analyzePhoto(base64, { steps, categoryAddress, model })
          │  ЕДНА заявка връща ДВА резултата:
          ▼
       {
         watermark: { present, rawText, date, time, city, address, other },
         content:   { sceneDescription, detectedElements },
         stepMatches: [ { stepId, verdict, confidence, matched[], missing[], reason } ],
         addressCheck: { verdict: 'same'|'different'|'unknown', note }
       }
          │
          ▼
   ai-sorter.resolvePhoto(photo, exif, aiResult, category)
          │
          ├─ effectiveDateTime = EXIF ?? watermark ?? null   (EXIF с приоритет)
          ├─ cross-check: EXIF vs watermark dateTime → discrepancy warning
          ├─ address check: different → status 'possible-other-site' (неприсвоена)
          ├─ best step = max confidence сред verdict 'match'/'partial'
          ├─ confidence ≥ праг (default 70%) → assigned; иначе → 'irrelevant'
          └─ warnings[] (частично съвпадение, разминаване, липса на време…)
          │
          ▼
   photo.aiAnalysis = { …цялата структура… }  → storage.savePhoto()
          │
          ▼
   Групиране по bestStepId → хронологична наредба вътре в стъпката
   → storage.updatePhoto({ categoryId, stepId, position })
   → обновяване на category.steps[].photoIds
          │
          ▼
   Доклад + баджове в галерията + AI панел в preview
```

- Оригиналният `photo.file` **никога не се променя** от AI анализа.

## 4. Функционални изисквания

> Приоритети: **MVP** = задължително за v1.2.0 · **Phase 2** = следваща итерация · **Future** = идея

### FR-1 · Модал „AI сортиране" (MVP)
- Нов бутон **„🤖 AI сортиране"** в лентата на Галерията (до „Обработи избраните"), активен при ≥1 снимка.
- Модалът съдържа:
  - **Избор на категория** (dropdown на съществуващите категории; показва брой стъпки).
  - **Преглед на стъпките** на избраната категория (read-only списък: име + „Описание" + необходим брой) — за да вижда потребителят какво ще се сравнява.
  - **AI настройки:** endpoint, API key (password поле), model — **пре-попълнени от съществуващите per-category настройки** (`loadAISettings(categoryId)`). Полетата са редактируеми и се запаметяват за категорията.
  - **Индикатор за routing:** „🔑 Локален ключ → директна връзка (без Netlify)" или „🌐 Без ключ → Netlify proxy".
  - **Праг на увереност** (slider/number, default **70%**, настройваем).
  - **Force re-analysis** checkbox (пренебрегва кеша).
  - **Хинт:** „Препоръчително: снимки само от един обект. Галерията съдържа N снимки." + линк „Изчисти галерията" (използва съществуващото изтриване). **Не блокира** старта.
  - Бутони: **„▶ Стартирай AI анализ"**, „Отказ".
- **Валидация:** избраната категория трябва да има ≥1 стъпка с попълнено „Описание"; иначе — ясна грешка/подсказка.

### FR-2 · Vision анализ — една заявка, два резултата (MVP)
- За **всяка** снимка в галерията се пуска **един** vision API call, който връща **едновременно**:
  1. **Извлечен воден знак** (дата, час, град, адрес, друг текст) — суров оригинален текст + нормализирани полета.
  2. **Анализ на съдържанието** + **съвпадение по стъпки** (вердикт, увереност, matched/missing, причина).
- Вход към модела: анализно копие на снимката (base64) + списък със стъпките (id, име, **„Описание" = очаквано съдържание**) + настроеният адрес на категорията (за адресната проверка).
- Изход: **стриктен JSON** (схемата в §3.4). При невалиден JSON → repair (извличане на `{…}`, премахване на markdown fences) → 1 повторен опит → иначе маркиране на снимката като `error` (без да спира batch-а).
- **Език на отговора:** вердиктите, причините и описанията са **на български**; суровият текст на водния знак се запазва **в оригинал** (немски/др.).

### FR-3 · Извличане и запаметяване на метаданни (MVP)
- Извлечените от водния знак стойности (дата, час, град, адрес, други) се записват в `photo.aiAnalysis.watermark`.
- Нормализация на дата/час от немски формати (`DD.MM.YYYY`, `HH:MM`, `DD.MM.YY HH:MM:SS` и др.) → ISO `YYYY-MM-DD` / `HH:MM`.
- Данните са **трайни** (IndexedDB) и **преизползваеми** за по-нататъшна обработка на която и да е снимка (FR-12).

### FR-4 · Кръстосана проверка EXIF ↔ воден знак (MVP)
- За всяка снимка се чете EXIF (`exif.readExifData` — съществуващ модул).
- **Приоритет на ефективното време:** `EXIF > воден знак > никакво` (само AI съдържание).
- Ако **и двата** източника имат дата/час и се разминават с повече от **толеранс (default 5 мин)** → **предупреждение** в доклада и в `aiAnalysis.warnings`.
- Ако няма нито EXIF, нито воден знак → разчитаме **само на AI анализа на съдържанието**; снимката се маркира „без времеви метаданни" (отива в края на хронологичната наредба).

### FR-5 · Адресна проверка (MVP)
- Сравнява се адресът от водния знак с настроения адрес на категорията (`category.enrichment.address`).
- **Семантично сравнение чрез AI** (в същата заявка): разпознава един и същ адрес в различни формати/езици (`Hauptstr. 5` = `Hauptstraße 5`; `ул. Витоша 10` = `Vitosha 10`). Връща `same` / `different` / `unknown`.
- **`different` → предупреждение + снимката остава НЕприсвоена** с бадж **„възможен друг обект"** — потребителят решава ръчно. *(Фиксирано решение.)*
- **`unknown`** (няма адрес във водния знак или категорията няма настроен адрес) → **не блокира**; бележка в доклада.
- **`same`** → продължава към съвпадение по съдържание.

### FR-6 · Съвпадение по съдържание (MVP)
- **Полето „Описание" на всяка стъпка** (модал „Нова стъпка") се използва като **промпт за очакваното съдържание**. Без нова библиотека/шаблони.
- AI връща за всяка стъпка: `verdict` (`match`/`partial`/`no-match`), `confidence` (0–100), `matched[]` (кое точно съвпада: дупка, скъсан кабел, наранена тръба…), `missing[]` (кое не съвпада), `reason` (кратко обяснение на български).
- **Водещ критерий е съдържанието** (не адресът/времето). Адресът и времето са допълнителни филтри/предупреждения.
- Избира се **най-добрата стъпка** = най-висока увереност сред `match`/`partial`.
- `partial` → присвоява се, но с **предупреждение „частично съвпадение"** + кои елементи липсват.

### FR-7 · Автоматично присвояване + хронология (MVP)
- **Праг:** увереност ≥ **70%** (настройваем в модала) → присвояване; под прага или `no-match` навсякъде → **„нерелевантна"**.
- **Всички** съвпадащи снимки се присвояват — „необходим брой снимки" е **МИНИМУМ, не таван**. *(Фиксирано решение.)*
- **Наредба вътре в стъпката:** по `effectiveDateTime` възходящо (хронологично). Снимки **без време** → в края, подредени по увереност; маркирани с предупреждение.
- Позициите се записват през **съществуващия** `storage.updatePhoto({ categoryId, stepId, position })` + обновяване на `category.steps[].photoIds`.
- **Глобалната номерация** на категорията (стъпка ред → позиция) се запазва съвместима със съществуващата логика в `main.js`/`ui.js`.
- След присвояване — **ръчна корекция** остава възможна (drag & drop, модал „Присвои снимки" — без промяна).

### FR-8 · Хронологична проверка МЕЖДУ стъпките (MVP)
- След разпределението се проверява **времевата логика между последователните стъпки** (напр. „Заварено" трябва да е преди „Ремонт").
- **Евристика:** ако най-късното време на по-ранна стъпка > най-ранното време на по-следваща стъпка → **предупреждение за аномалия** в доклада (кои снимки/стъпки се застъпват).
- **Само предупреждение** — НЕ пренарежда автоматично между стъпките. *(Фиксирано решение.)*

### FR-9 · Баджове за статус в галерията (MVP)
| Статус | Бадж | Цвят/икона | Поведение |
|---|---|---|---|
| `assigned` | „AI ✓ #N" (позиция) | зелено | присвоена към стъпка |
| `irrelevant` | „нерелевантна" | сиво/червено | неприсвоена + причина от AI (видима при преглед) |
| `possible-other-site` | „възможен друг обект" | оранжево | неприсвоена + адресна бележка |
| `error` | „AI грешка" | червено | analiza не успя; бутон „Опитай отново" |
- Баджовете са **текстови** (не само цветови) за достъпност.
- Причината/вердиктът се виждат в **preview модала** (FR-11) и в **доклада** (FR-10).

### FR-10 · Доклад (MVP)
- След обработка се отваря **доклад модал** (потребителят може да го затвори/пропусне — не е задължителен за четене).
- **Обобщение:** брой присвоени / нерелевантни / възможен друг обект / грешки; брой предупреждения; използван модел и routing.
- **По снимка:** тумбнейл, име, → стъпка (или статус), увереност %, вердикт + причина, matched/missing, **цялата извлечена мета информация** (воден знак: дата/час/град/адрес; EXIF; ефективно време + източник), списък с предупреждения.
- **Секция „Хронологични аномалии"** (FR-8).
- **Експорт JSON** (бутон „📤 Експорт JSON") — целият доклад като файл. *(PDF/печат → Phase 2.)*

### FR-11 · Метаданни в галерията и preview (MVP)
- **Галерията показва извлечената мета информация за всяка снимка** (изрично изискване):
  - Компактен overlay/info на картата: дата/час, град (ако има).
  - Пълен **„AI анализ" панел в preview модала** (двойно клик): суров воден знак, нормализирани полета, EXIF, ефективно време + източник, описание на сцената, открити елементи, вердикт/увереност по стъпки, адресна проверка, предупреждения.
- Данните се четат от `photo.aiAnalysis` (без повторен API call).

### FR-12 · Преизползване на метаданните за обработка (MVP — базово; Phase 2 — разширено)
- Извлечените стойности (дата, час, адрес) са **налични като източник** за съществуващия watermark/enrichment pipeline.
- **MVP:** при обработка на категория (`processCategoryPhotos`), ако снимката има `aiAnalysis.effectiveDateTime` / `aiAnalysis.watermark.address` и **няма** ръчен enrichment override → използва тях за водния знак (ред: **ръчен enrichment > EXIF > AI воден знак**).
- **Phase 2:** UI за избор на източник per снимка/категория (provenance), показване в enrichment модала.

### FR-13 · Кеширане и повторен анализ (MVP)
- `aiAnalysis` се кешира в IndexedDB.
- **Кешът е валиден**, ако: същият `model` + същата `stepSignature` (hash на id+описания на стъпките + адрес на категорията) + не е отметнат „Force".
- При валиден кеш → **без нова API заявка** (спестява време/токени); снимката се преразпределя според кеширания резултат.
- „Force re-analysis" → пълно повторно анализиране.
- Промяна в описанията на стъпките → `stepSignature` се променя → автоматично повторно анализиране.

### FR-14 · Хибриден routing + устойчивост + Rate Limiting (MVP)
- Локален ключ → директно; без ключ → proxy (§3.2).
- **Retry с backoff** при 429/5xx (до 2 опита).
- **Sequential processing (concurrency = 1)** — единственият безопасен режим за Groq free tier.
- **Token-aware throttle (GroqTokenThrottle):**
  - Изчислява минимален интервал от **TPM лимита** (8,000 tokens/min), не от RPM.
  - 1 снимка ≈ 2,550 токена (2,048 image + ~500 prompt/response) → **~19 сек интервал** (с 20% буфер).
  - Резултат: **~3 снимки/мин**, 30 снимки ≈ **10 мин**.
  - Съхранява `dailyCount` и `lastResetDate` в localStorage/IndexedDB за проследяване на дневен квота (1,000 req/ден).
- **Batch size:** 1 снимка/заявка (по подразбиране); конфигурируем до **3 снимки/req** (тогава интервалът се увеличава пропорционално).
- **Per-photo error isolation:** грешка в една снимка НЕ спира batch-а; маркира се `error`, продължава се.
- **Прогрес с ETA:** „Обработка 12/30... Оставащи ~6 мин“.
- **Quota UI:** показване на оставащ дневен квота; предупреждение при <50 оставащи заявки.
- **Ясни съобщения** при липса на ключ И липса на proxy (напр. локален dev без Netlify): „Няма AI ключ. Въведете ключ или deploy-нете Netlify proxy.“

### User Stories (MVP)
- **US-1:** Като технически ръководител, искам да заредя 30 снимки от един обект, да избера категория „Авария" и с един клик AI да ги разпредели по стъпките, за да спестя часове ръчен преглед.
- **US-2:** Като потребител, искам да виждам за всяка снимка извлечените дата/час/адрес от водния знак, за да ги използвам по-късно при обработка.
- **US-3:** Като потребител, искам доклад с увереност и причина за всяко разпределение, за да се доверя на резултата и да коригирам при нужда.
- **US-4:** Като потребител, искам снимки от друг адрес да НЕ се смесват с текущия обект, а да са маркирани „възможен друг обект".
- **US-5:** Като потребител без собствен API ключ, искам да използвам сървърния ключ през Netlify, без да въвеждам нищо.
- **US-6:** Като потребител, искам прегледаните вече снимки да не се анализират повторно (кеш), освен ако изрично поискам.

## 5. Нефункционални изисквания

### 5.1 Производителност
- **Downscale преди изпращане:** анализно копие max **1600px** дълъг ръб, JPEG q≈0.8 (оригиналът не се пипа). Намалява токени/латентност/памет.
- **Sequential processing (concurrency = 1)** — задължителен за Groq free tier.
- **Token-aware throttle (GroqTokenThrottle):**
  - Базиран на **TPM = 8,000 tokens/min** (реален bottleneck), не на RPM.
  - 1 снимка ≈ 2,550 токена → **~19 сек интервал** (с 20% буфер) → **~3 снимки/мин**.
  - 30 снимки ≈ **10 мин** общо време.
- **Batch size:** 1 снимка/заявка (default); конфигурируем до 3 (тогава интервалът се увеличава).
- **Кеш:** валиден `aiAnalysis` → 0 мрежови заявки (FR-13) — спестява квота и време.
- **Дневен квота:** 1,000 req/ден (организационно ниво) — проследява се локално; UI предупреждение при <50 оставащи.
- **Памет:** Canvas се освобождава след всяка снимка; base64 не се задържа след заявката.

### 5.2 Сигурност и поверителност
- **API ключът** се пази **локално** (IndexedDB, съществуващият per-category механизъм). Никога не се изпраща към трети страни освен към AI доставчика (при директния път) или към собствения Netlify proxy (при fallback).
- **Снимките** отиват **само** до Groq (директно) или през Netlify транзит → Groq (proxy). **Няма телеметрия, няма друго външно изпращане.**
- Netlify proxy **не записва/логва** снимките (транзит в паметта).
- **Без сървърно съхранение** на снимки/метаданни — всичко в браузъра.
- Паролата/ключът в UI е `type=password`; не се логва в console.

### 5.3 Достъпност
- Баджовете са **текстови** (не само цветови).
- Модалите: `role=dialog`, `aria-modal`, фокус капан, Escape за затваряне (следват съществуващия pattern).
- Прогресът: `aria-live`, `<progress>` с label.
- Клавиатурна навигация в модала/доклада.

### 5.4 Офлайн / устойчивост
- **AI изисква интернет.** При офлайн → ясно съобщение; **ръчният поток (а) НЕ се засяга** и работи офлайн както досега.
- PWA service worker **не трябва да кешира** AI заявките (dynamic, non-cacheable) — уверете се, че runtime caching не ги intercept-ва.
- Грешка в една снимка не чупи batch-а.

### 5.5 Съвместимост
- Без промяна на съществуващите данни/поведение (ръчен поток, воден знак, enrichment, QR).
- `aiAnalysis` е **адитивно** поле — стари снимки без него продължават да работят.
- Съвместимост с **едновременната работа на другия агент** (виж §6.3).

## 6. Ограничения

### 6.1 Какво НЕ правим (MVP)
- ❌ **Не трием** снимки автоматично (нерелевантните остават в галерията).
- ❌ **Не променяме оригиналните файлове** при AI анализ (само анализно копие).
- ❌ **Не пренареждаме автоматично МЕЖДУ стъпките** при хронологична аномалия — само предупреждение.
- ❌ **Не изискваме преглед преди присвояване** — разпределението е автоматично; докладът е след това (по избор).
- ❌ **Без PDF/печат на доклада** в MVP (само екран + JSON експорт).
- ❌ **Без нова библиотека от шаблони** за очаквано съдържание — използва се съществуващото „Описание" на стъпката.
- ❌ **Без сървърна БД/облак** за снимки.
- ❌ **Без автоматично изгаряне на воден знак** веднага след AI сортиране — обработката остава отделна стъпка (както сега).

### 6.2 Технически ограничения
- **Netlify sync function body limit ≈ 6MB.** Downscale-нато JPEG (~150–500KB) → base64 (~200–700KB) е безопасно. При огромни оригинали → downscale-ът гарантира лимита.
- **Groq rate limits** (RPM/TPM, особено free tier) → concurrency 2 + retry/backoff.
- **Vision наличност на модела:** `qwen/qwen3.8-27b` трябва да поддържа vision в Groq — **верифицира се във Фаза 0**; моделът е конфигурируем, така че при липса се заменя с vision-capable модел.
- **JSON надеждност:** LLM може да върне невалиден JSON → repair + retry + error isolation.
- **Немски водни знаци:** разнообразни формати на дата/час/адрес → нормализацията трябва да е толерантна; суровият текст се пази винаги.

### 6.3 Организационни ограничения (⚠️ друг агент)
- `src/core/ai.js` е **празен (0 байта)**, но се import-ва от `main.js`/`ui.js`; AI настройките реално са в `geo-weather-enricher.js`. Друг агент вероятно рефакторира.
- **Стратегия:** новата функционалност се пише в **нови файлове** (`ai-vision.js`, `ai-sorter.js`). Настройките се четат през **адаптер**, който работи и с текущото състояние (`geo-weather-enricher.js`), и с евентуалния бъдещ `ai.js` — за да не се счупи при рефакторинга.
- **Минимални пачове** по `main.js`, `ui.js`, `index.html`, `storage.js` (добавяне, не пренаписване).
- **Преди имплементация:** @coder да се синхронизира с другия агент / да провери актуалното състояние на `ai.js`.

## 7. План за изпълнение (стъпка по стъпка)

> Всеки етап има **зависимости** и **критерий за завършване**. @coder изпълнява последователно; @reviewer проверява след всеки етап.

### Фаза 0 · Координация и верификация (блокираща)
**Задачи:**
1. Проверка на актуалното състояние на `src/core/ai.js` и къде живеят AI настройките (синхронизация с другия агент).
2. **Верификация на vision модела:** тестова заявка към Groq с `qwen/qwen3.8-27b` + изображение (`image_url` base64). Потвърждава се: (а) моделът поддържа vision, (б) форматът на отговора, (в) CORS за директни browser заявки.
3. Ако моделът няма vision → избор на конфигурируем vision-capable заместител (документира се).
4. Потвърждаване на Netlify proxy наличност/deployment за fallback.

**Зависимости:** няма.
**Критерий за завършване:** успешна тестова vision заявка (директно и/или през proxy); ясен списък с налични модели; решение къде се четат настройките.

### Фаза 1 · AI vision core (`src/core/ai-vision.js`)
**Задачи:**
1. `downscaleToBase64(blob, maxEdge=1600, quality=0.8)` — Canvas → JPEG base64 (оригиналът не се пипа).
2. `buildVisionPayload({ imageBase64, steps, categoryAddress, model })` — system prompt (§Приложение A) + user content (image_url + текст със стъпките).
3. `analyzePhoto(...)` — **хибриден routing:** чете настройките (адаптер); има ключ → директен fetch; няма → proxy.
4. `parseAndValidateResult(raw)` — JSON parse + schema validation + repair (fences/извличане) + 1 retry.
5. **`GroqTokenThrottle` клас:**
   - Конструктор: `{ tpm=8000, rpm=30, rpd=1000, tokensPerImage=2048, baseTextTokens=500, batchSize=1 }`
   - `minIntervalMs = ceil((batchSize * tokensPerImage + baseTextTokens) / tpm * 60000) * 1.2`
   - `async wait()` — чака до `minIntervalMs` от последната заявка; проверява `dailyCount` (reset на полунощ); хвърля грешка при изчерпан дневен квота.
   - `getStatus()` → `{ remainingToday, nextAvailableAt, estimatedTotalTime(photosLeft) }`
   - Съхранява `dailyCount`, `lastResetDate`, `lastRequestAt` в localStorage/IndexedDB (преживява reload).
6. **Sequential queue** в `analyzePhotosBatch(photos[], ...)`:
   - За всяка снимка: `await throttle.wait()` → `fetch` → `parse` → callback с прогрес.
   - `concurrency = 1` (hardcoded); batch size конфигурируем (default 1).
   - `retry/backoff` при 429/5xx (до 2 опита) — throttle се ресетира при 429.
7. **Разширение на `netlify/functions/ai-process.js`:** `action:'analyze-image'` приема `image` (base64) + `context` (steps, address) → строи vision messages със сървърния ключ. Запазва съществуващите текстови действия.

**Зависимости:** Фаза 0.
**Критерий:** една снимка се анализира успешно и по двата пътя; връща валиден JSON по схемата; невалиден JSON се repair-ва; 429 се retry-ва; throttle спазва TPM/RPD лимитите; quota status се показва в UI.

### Фаза 2 · Данни и съхранение
**Задачи:**
1. Дефиниране на `aiAnalysis` схемата (§3.4) като обект/константа.
2. `storage` helpers: `saveAiAnalysis(photoId, analysis)`, `getAiAnalysis(photoId)` (преизползват `savePhoto`/`getPhoto`/`updatePhoto`).
3. `stepSignature(category)` — hash на стъпки (id+описание) + адрес; валидност на кеша (FR-13).
4. Настройка за **праг на увереност** (default 70) в settings store (per-category или глобално).
5. Адаптер за AI настройки (съвместим с текущия `geo-weather-enricher.js` и бъдещия `ai.js`).

**Зависимости:** Фаза 1 (схемата).
**Критерий:** `aiAnalysis` се записва/чете от IndexedDB; кешът се разпознава като валиден/невалиден; прагът се запаметява.

### Фаза 3 · Sorting engine (`src/core/ai-sorter.js`)
**Задачи:**
1. `resolvePhoto(photo, exif, aiResult, category, threshold)`:
   - ефективно време (EXIF > воден знак > none) + cross-check + толеранс 5 мин.
   - адресна проверка (`different` → `possible-other-site`).
   - избор на best step (max confidence сред match/partial) + праг → `assigned`/`irrelevant`.
   - warnings (частично съвпадение, разминаване, без време…).
2. `assignPhotos(category, resolvedPhotos)`:
   - групиране по bestStepId; хронологична наредба вътре в стъпката (nulls last).
   - запис на позиции през `storage.updatePhoto` + обновяване на `steps[].photoIds`.
   - съвместимост с глобалната номерация.
3. `checkInterStepChronology(category, assigned)` → аномалии (FR-8).
4. `buildReport(...)` → структура за доклада + JSON експорт.
5. **Batch оркестрация (sequential):**
   - За всяка снимка: EXIF + downscale → `ai-vision.analyzePhoto` (через throttle) → resolve → накопява резултати.
   - Прогрес callback на всяка стъпка: `{ current, total, percent, etaMs, throttleStatus }`.
   - Per-photo error isolation; грешка не спира batch-а.
   - Кеш (FR-13) се проверява **преди** throttle — при валиден кеш: 0 мрежови заявки, momentанен прогрес.

**Зависимости:** Фази 1, 2.

### Фаза 7 · Тестване и приемане
**Сценарии (задължителни):**
1. **§1.5 пример:** 5 снимки (2 „заварено“, 3 „ремонт“) → правилно разпределение + хронология.
2. **Адресно разминаване:** снимка с друг адрес → „възможен друг обект“, неприсвоена.
3. **Без метаданни:** снимка без EXIF и без воден знак → само AI съдържание; в края на наредбата.
4. **EXIF ↔ воден знак разминаване:** > 5 мин → предупреждение; EXIF важи.
5. **Повече от минимума:** 4 съвпадения при зададени 2 → всички присвоени.
6. **Нерелевантна:** съдържание извън всички стъпки / под прага → бадж + причина.
7. **Частично съвпадение:** `partial` → присвоена + предупреждение.
8. **Хронологична аномалия между стъпките:** „ремонт“ с по-ранен час от „заварено“ → предупреждение.
9. **Кеш:** повторен старт без force → 0 нови заявки; с променено описание → повторно анализиране.
10. **Routing:** с локален ключ → директно (без Netlify); без ключ → proxy.
11. **Устойчивост:** невалиден JSON от модела → repair/error isolation; 429 → retry; офлайн → ясно съобщение, ръчният поток работи.
12. **Регресия:** ръчно присвояване, drag & drop, воден знак, enrichment, QR — без промяна.
13. **Rate limiting & Quota:** 30 снимки последователно → ~10 мин, throttle спазва TPM/RPD; quota UI показва оставащо квота; при изчерпан дневен квота → ясно съобщение + „Опитай утре“; кеш на 15 снимки → вторият run за <1 мин.

**Зависимости:** Фаза 6.
**Критерий:** всички сценарии минават; @reviewer одобрява; няма регресия.

Ти си AI анализатор на снимки за документация на аварии/ремонти.

## Приложение B · Илюстративен псевдокод на разпределението
> **Само илюстрация** — не е функционален код.

```
GroqTokenThrottle:
  tpm = 8000, rpm = 30, rpd = 1000
  tokensPerImage = 2048, baseTextTokens = 500, batchSize = 1
  minIntervalMs = ceil((batchSize * tokensPerImage + baseTextTokens) / tpm * 60000) * 1.2  // ~19 сек
  dailyCount, lastResetDate, lastRequestAt  // в localStorage/IndexedDB

  async wait():
    if now > lastResetDate: dailyCount = 0; lastResetDate = nextMidnight()
    if dailyCount >= rpd: throw "Daily quota exhausted"
    elapsed = now - lastRequestAt
    if elapsed < minIntervalMs: sleep(minIntervalMs - elapsed)
    lastRequestAt = now
    dailyCount++

throttle = new GroqTokenThrottle()

за всяка снимка (SEQUENTIAL, concurrency = 1):
    if validCache(photo, steps, model):   // FR-13: stepSignature hash
        resolved = cachedResult
        progress(current, total, eta=0)   // momentанен
        continue

    await throttle.wait()                 // спазва TPM + RPD
    exif  ← readExifData(photo.file)
    b64   ← downscale(photo.file, 1600, 0.8)
    ai    ← analyzePhoto(b64, steps, categoryAddress)  // 1 req, 1 снимка
    resolved ← resolvePhoto(photo, exif, ai, category, праг)
    запиши photo.aiAnalysis = resolved
    progress(current, total, etaMs=throttle.estimatedTotalTime(remaining))

// resolvePhoto:
effectiveTime = exif.dateTime ?? parse(ai.watermark.date, ai.watermark.time) ?? null
ако exif и watermark имат време и |разлика| > 5мин → warning
ако ai.addressCheck.verdict == "different" → status="possible-other-site", върни (неприсвоена)
best = argmax(confidence) сред stepMatches с verdict in {match, partial}
ако best.confidence >= праг → status="assigned", bestStepId=best.stepId
иначе → status="irrelevant"
ако best.verdict=="partial" → warning("частично съвпадение", best.missing)
ако effectiveTime==null → warning("без времеви метаданни")

// assign:
групирай assigned по bestStepId
за всяка стъпка: сортирай по effectiveTime asc (nulls в края, tie-break confidence desc)
позиции 1..n → storage.updatePhoto({categoryId, stepId, position})
обнови category.steps[].photoIds

// inter-step:
за последователни стъпки i, i+1 с времена:
    ако max(time[i]) > min(time[i+1]) → anomaly warning в доклада

// report:
обобщение + per-photo детайли + аномалии → JSON експорт
```

## Приложение C · Речник
| Термин | Значение |
|---|---|
| **Воден знак (watermark)** | Текст/графика, изгорени върху снимката (дата, час, адрес, номер…) |
| **EXIF** | Метаданни в image файла (камера, дата/час, GPS) |
| **Ефективно време** | Избраното време за хронология: EXIF > воден знак > никое |

| **Вердикт** | AI преценка: match / partial / no-match |
| **Увереност (confidence)** | 0–100%; праг default 70% |
| **Routing** | direct (локален ключ → Groq) / proxy (Netlify → Groq) |
| **stepSignature** | Hash на стъпките+адреса; валидира AI кеша |
| **Нерелевантна** | Снимка без съвпадение/под прага → неприсвоена + бадж |
| **Възможен друг обект** | Адресно разминаване → неприсвоена + бадж |
